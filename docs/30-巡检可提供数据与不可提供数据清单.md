# 巡检可提供数据与中控不可提供数据清单

> 依据：`docs/29-巡检数据来源与MCP调用情况.md`、当前事实采集/归一化代码、巡检 Result Envelope 和历史中控兼容载荷。
>
> 目的：明确“中控需要什么”与“巡检实际负责什么”的边界，避免把暂时缺数误报为永久无能力，也避免让巡检伪造执行结果。

## 1. 判断口径

本文把字段分为四类：

1. **当前可直接提供**：当前采集链路能够取得，并且能进入巡检事实或中控载荷。
2. **可计算提供**：不是 MCP 原始字段，但可由已取得事实按明确公式计算；必须标记为计算值。
3. **理论可提供、当前不能稳定承诺**：代码或 MCP 链路已有入口，但当前覆盖率、异步回填或运行合同不足。
4. **巡检完全不能提供**：不是“这次没取到”，而是属于执行系统、复盘系统、其他 Agent 或巡检没有权限/粒度的数据。

“完全不能提供”仅针对巡检职责和当前系统边界，不表示中控永远不能拥有这些数据；这些数据应由中控执行面、广告/价格/库存/Listing 专业 Agent 或平台回执链路提供。

## 2. 当前巡检能提供的内容

### 2.1 经营单元和展示信息

| 数据 | 当前来源/处理 | 可给中控的字段 |
|---|---|---|
| 经营单元身份 | 全量分页经营单元目录，身份键固定为 `shopId + siteCode + parentAsin + parentSellerSku` | `shopId`、`siteCode`、`parentAsin`、`parentSellerSku` |
| 产品名称 | `erp_listing_product_info`/`erp_asin_full_detail` 归一化 | `productName` |
| 子 ASIN、子 SKU、父子关系、Listing 状态 | `erp_listing_product_info`，子体扩展完成后补充 | `factSnapshots` 中的子体明细、状态、父子关系 |
| 负责人 | `erp_listing_product_info` 每个子 SKU 的 `principalUserId/principalUserName` 聚合；只有单一负责人时写 `ownerUserId` | `ownerUserId`；多人或缺失时留空并记录缺口 |
| 主图/图片 | 只取 `erp_listing_product_info` 中标记为流量入口的 `picUrl`；不使用店铺 Logo | `productPicUrl`、Listing 快照中的图片来源和图片状态 |
| Seller ID/Buy Box | `erp_listing_product_info` 中合并的 `SELLING_PARTNER_ID`、Buy Box 字段 | 事实快照中的 `own_seller_id`、`buy_box_owner`、`buy_box_seller_id`；不能在字段冲突时猜选 |

代码依据：`facts/normalizer.py:602-870`；中控模型：`core/control_center_contracts.py:35-65`。

负责人、商品图片属于巡检可提供字段；当前样本覆盖率不足时传空并记录数据缺口，不代表字段不支持。

### 2.2 经营、广告、库存和质量事实

| 数据域 | 当前可提供的原始/归一化字段 |
|---|---|
| 销售 | 逐日 `salesAmount`、`salesQuantity`、`orderQuantity`，以及销售日期、数据新鲜度、有效天数 |
| 广告 | `adCost`、`adSalesAmount`、`adOrder`、ACOS、目标 ACOS、目标日预算、广告零销售天数；广告配置中的经营标签可作为原始事实或明确标记的 fallback |
| 流量 | 业务报告中的 Sessions、订单商品数、转化率；自然订单窗口聚合值；逐日自然/广告序列当前按策略停用，不得假造 |
| 利润 | 单位贡献利润、毛利率、产品成本/佣金/履约费等能从实际响应取得的成本项；`contributionProfit` 可进入中控指标 |
| 库存 | FBA 可售、在途、预留、不可售、采购在途、总库存、超龄库存及仓储费用；库存覆盖天数为计算值 |
| 价格/促销 | 子体价格、划线价、Coupon、促销、折扣类型、促销活动返回；平台活动空数据必须保留为空/缺口 |
| 质量/合规/评论 | 评分、评论数、转化率、退款率、类目排名、账户健康问题、近期差评；父级评分/评论数在前台详情缺失时由 `listing_basic_info` 补充 |

代码依据：`facts/normalizer.py:875-1489`；采集计划：`facts/collector.py:130-282`。

### 2.3 巡检结果

巡检可以提供：

- `factSnapshots`：销售、利润、库存、价格、Listing 等事实快照，带来源、窗口、质量状态、完整度和缺口；
- `anomalies`：异常类别、异常编码、目标类型/目标 ID、严重度、证据引用、根因状态；
- `details`：人工复核交接项、建议的观察窗口、风险和证据引用；
- `dataGaps`、`rawAnalysis`：数据缺口、字段覆盖、事实完整度、经营模式来源和计算口径；
- `businessModel/recommendedBusinessModel`：优先使用经营模式 Agent 的 `DECIDED` 结果；未 `DECIDED` 时只能使用明确标记的 `ADVERT_CONFIG_FALLBACK`，不能冒充 Agent 权威结论。

经营模式属于巡检可提供字段：OM Agent 的 `DECIDED` 结果为权威值，未 `DECIDED` 时按已标记的 fallback 规则处理。

历史兼容载荷中，`details` 已明确设置 `MANUAL_REVIEW_ONLY` 和 `autoExecutionAllowed=false`（`scripts/submit_real_patrol_to_control_center.py:465-486`、`:614-667`）。

## 3. 可以计算，但不能冒充 MCP 原始事实

| 计算值 | 计算口径 | 约束 |
|---|---|---|
| `contributionProfit` | `unit_contribution × salesQuantity` | 单位贡献利润或销量缺失时必须阻断/留空 |
| `profitRate` | 使用实际毛利率字段或已冻结的利润公式 | 不得用销售额减广告费等简化公式冒充净利润 |
| `monthly_completion_rate` | 当月已完成订单 ÷ 当月目标订单 | 月目标缺失时为 `null`，不能用默认目标 |
| `inventory_days_of_supply` | 可售库存 ÷ 平均日销量（30 日优先，7 日兜底） | 分母为 0/缺失时为 `null`，不写“无限天” |
| 自然订单 | 总订单 − 广告订单 | 仅能在两者同口径同日期行时计算；当前逐日流量序列按策略停用 |
| 中控标签枚举 | 将广告配置中文标签映射为中控枚举 | 未映射值保留 `unmapped` 和缺口，不猜枚举 |

## 4. 当前不能稳定承诺，但并非职责上完全不能提供

以下项目不能作为“当前全量已提供”向中控承诺，但有数据入口或代码支持，属于补数、运行合同或异步链路问题：

| 数据 | 当前状态 | 正确表述 |
|---|---|---|
| 月目标 | `erp_listing_monthly_goal` 最新成功约 `112/199`（56.28%） | “有入口但当前不稳定，缺失时降级” |
| 平台活动 | 工具调用成功但部分返回空数据（最新 63 个空） | “可判定部分促销，不可宣称活动全量覆盖” |
| 子体 Listing/促销/合规/评论 | 异步扩展链路已实现，最新报告生成时尚未完成回填 | “等待子体事实完成后重跑” |
| 关键词排名 | 有调用入口，但真实调用成功 `0/48` | “当前不可用，不输出排名结论” |
| 逐日自然/广告流量 | `natural_ad_flow` 默认被策略禁用 | “当前不采集逐日序列，不伪造趋势数据” |
| 完整巡检状态 | 最新 199 个快照均为 `PARTIAL`，平均完整度约 68.64% | “父级基础数据可用，完整点位尚未覆盖” |

这些项目属于“当前覆盖/可用性问题”，不能放入“完全不能提供”清单，否则会掩盖后续补数和联调空间。

## 5. 巡检完全不能提供给中控的数据

以下是本次差距判断的核心清单。巡检可以提交异常和人工交接，但不能生产、承诺或伪造以下数据。

### 5.1 任何业务动作的实际执行结果

巡检没有广告、价格、库存或 Listing 的写权限和执行回执，因此不能提供：

- 实际调价、调预算、调 Bid、启用/暂停广告后的平台执行状态；
- 实际创建、修改或取消促销后的平台回执；
- 实际补货、停止补货、清货、移除库存后的执行状态和数量；
- 实际修改标题、五点、A+、图片、属性、变体关系后的平台回执；
- Amazon/ERP 返回的执行订单号、任务号、平台 request ID、失败原因、重试结果和最终生效时间。

巡检输出的 `ProposalDetail` 只是人工复核建议。当前实现强制 `MANUAL_REVIEW_ONLY`、`PENDING_APPROVAL`，`autoExecutionAllowed` 为 `false`；这不是执行结果。

### 5.2 批准计划、执行回执和动作后复盘事实

`approvedPlan`、`executionReceipts` 属于中控审批/执行反馈链路（见 `core/control_center_contracts.py:579-610`），不是巡检采集产物。巡检最多消费中控回流的回执引用，并在下一轮重新采集事实；不能自行填写：

- 谁批准了哪一项动作、批准时间和审批版本；
- 哪个执行 Agent 接收/执行了动作；
- 动作是否成功、部分成功、失败或被平台拒绝；
- 动作后的真实销售、利润、库存变化及成功标准是否达成；
- 执行偏差、平台异步生效、人工改动和动作幂等结果。

### 5.3 广告实体级执行对象和执行状态

当前巡检主身份是“店铺 × 站点 × 父 ASIN × 父 SKU”，采集事实也以父经营单元和子 ASIN 为主。当前没有可供巡检负责的、完整且可验证的广告实体主键链路，因此不能向中控承诺：

- Campaign ID、Ad Group ID、Keyword/Target ID 的完整层级关系；
- 每个广告实体的当前 Bid、预算、投放状态、匹配类型和 placement 状态；
- 某条异常对应的唯一广告实体执行对象；
- 广告动作逐条提交、逐条执行和逐条验证状态。

巡检可以依据父级广告花费、广告销售额、广告订单、ACOS 和配置目标识别异常，但这不等于拥有广告执行对象。

### 5.4 自动执行权限和“已执行”承诺

巡检的执行就绪状态不会生成 `READY_AUTO`，当前载荷明确写入 `autoExecutionAllowed=false`。因此不能提供：

- “系统已自动执行”的声明；
- “中控收到建议即可自动执行”的授权；
- 未经审批的动作状态 `APPROVED`、`EXECUTING`、`SUCCEEDED`；
- 任何把巡检建议转换为线上变更的权限证明。

### 5.5 运营管理配置表作为巡检身份或权威归属来源

巡检不使用“运营管理 ASIN 配置表”作为经营单元清单、负责人或唯一归属的权威来源。经营单元应来自全量 Listing 分页目录；负责人只取 `erp_listing_product_info` 的 ASIN 负责人字段并按规则聚合。若中控要求该配置表中的额外运营归属、运营分组或管理关系，当前巡检不能以该表名义提供，也不能用它回填缺失负责人。

这不影响巡检提供 `ownerUserId`：负责人字段有值时可以传；无值时必须传空并记录缺口。

### 5.6 完整覆盖和未来结果保证

巡检不能提供以下“保证型数据”：

- “所有经营单元已发现且无漏数”；
- “所有子 ASIN 扩展点位已完成”；
- “所有巡检规则均已判定”；
- “经营模式一定存在”；
- “异常建议执行后一定改善”；
- “MCP 调用成功率等于数据可用率”。

这些是运行质量或业务结果结论，必须以分页审计、事实质量、执行回执和复盘结果为证据，不能由巡检载荷直接宣称。

## 6. 字段责任边界

| 中控需要的内容 | 巡检能否提供 | 责任方/处理方式 |
|---|---|---|
| 经营单元身份、产品展示、负责人 | 可以，缺失时留空并报缺口 | ERP Listing MCP；负责人来自 ASIN 字段 |
| 销量、订单、销售额、广告指标、库存、质量 | 可以，按事实质量降级 | AZ MCP + Normalizer |
| 贡献利润、利润率、库存天数、月目标完成率 | 可以计算，必须保留计算口径 | 巡检归一化层 |
| OM Agent 经营模式 | 可以消费 `DECIDED`；非 `DECIDED` 只能 fallback | 经营模式 Agent 权威，广告配置仅兜底 |
| 异常、证据、数据缺口、人工复核建议 | 可以 | 巡检 Agent |
| 批准计划、审批记录 | **不可以** | 中控审批/运营决策面 |
| 调价/调预算/Bid/广告启停执行结果 | **不可以** | 价格/广告执行 Agent + ERP/Amazon 回执 |
| 补货/清货/Listing 修改执行结果 | **不可以** | 库存/Listing 执行 Agent + 平台回执 |
| Campaign/Ad Group/Keyword 级执行对象 | **当前不可以承诺** | 广告数据/执行 Agent 提供完整实体主键 |
| `executionReceipts`、动作后效果、执行偏差 | **不可以自产** | 中控反馈 Inbox/复盘链路 |
| 全量覆盖、动作成功、经营改善保证 | **不可以宣称** | 由各系统提供可验证证据 |

## 7. 给中控的落地建议

1. 中控接收接口应把巡检结果和执行结果分开：巡检只提交事实、异常、证据、缺口和人工交接。
2. `approvedPlan`、`executionReceipts`、动作状态和复盘结果应由中控/执行 Agent 产生，再通过反馈接口回流。
3. 中控展示层可以接收 `ownerUserId=null`、`productPicUrl=null`、`businessModel=null`，同时读取 `dataGaps` 和 `rawAnalysis`，不要用默认值掩盖缺口。
4. 经营模式字段按权威优先级处理：OM Agent `DECIDED` > 明确标记的 `ADVERT_CONFIG_FALLBACK` > 空值；不能反向覆盖。
5. 对 Campaign/Ad Group/Keyword 级动作，应由广告 Agent 提供稳定实体主键、当前值、执行回执和验证结果，巡检只引用异常证据。
