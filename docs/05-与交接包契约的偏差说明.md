# 与输入文档的偏差说明

本次交付有两份输入：

- **A**：《Amazon运营闭环技术交接包 20260728》（含 `contracts/` 机器契约、`规范/`、ADR）
- **B**：《Amazon运营闭环：巡检 Agent 改造优化与核心代码方案 v1.0》

两份文档在若干处不一致。凡有冲突，本项目的取舍原则是：

> **机器可校验的契约 > 设计文档叙述 > 实现方案示例代码**

理由：`contracts/*.json` 是被 `tests/test_contract_registry_consistency.py`
守着的机器权威源，中控和其它 Agent 也照它实现。代码跟着叙述走，
上线时对不上的是接口。

下面逐条列出偏差、取舍和影响。

---

## D-01：严重度枚举 `DATA_GAP` vs `DATA_INSUFFICIENT`

| 来源 | 取值 |
|---|---|
| 方案 B §6 示例代码 | `Literal["S0", "S1", "S2", "DATA_GAP"]` |
| 契约 A `inspection-signal.v2.schema.json` | `["S0", "S1", "S2", "DATA_INSUFFICIENT"]` |

**采用**：`DATA_INSUFFICIENT`（契约）。

**影响**：`core/enums.py` 的 `Severity` 用契约值；
`LegacyRuleAdapter.SEVERITY_MAP` 把旧的「配置待补」「数据不足」都映射到它。
契约测试 `test_severity_uses_contract_value_not_plan_value` 断言
`DATA_GAP` 不得出现。

**如果坚持用方案值**：产出的信号无法通过 `inspection-signal.v2` 校验，中控会拒收。

---

## D-02：广告 Agent —— 自动调用 vs 治理冻结 ⚠ 最重要的一条

| 来源 | 立场 |
|---|---|
| 方案 B §1、§5.1、§11、§16 | 巡检主链路**调用广告 Agent**，把广告建议纳入综合分析 |
| 交接包 A 不变量 10 / Ontology A13 / `capability-registry.rollout_status` / `operating-policy-registry.governance` | 广告 Agent **FROZEN**，不得自动调用，只能人工交接 |

这是硬冲突，不是措辞差异。交接包 02 §实施纪律甚至写了
「广告 Agent 的改造必须单独立项，不夹带进入本项目」。

**采用**：**两个都实现，用开关切换，默认服从治理约束。**

- `AdvertisingAgentClient` 按方案 §11 **完整实现**（合同、一致性校验、错误码齐全）；
- 是否真的发起调用由 `settings.yaml` → `advertising_agent.rollout_status` 控制；
- **默认 `FROZEN`**，此时 `propose()` 抛 `AdvertisingAgentFrozen`，
  编排器捕获后产出人工交接指令：
  `next_capability=ADVERTISING_DECISION_EXECUTION`、
  `reason_code=ADVERTISING_ACTION_REQUIRED`、`routing_mode=HUMAN_ONLY`；
- 改成 `ENABLED` 即切到方案的自动链路，**不需要改代码**。

**额外保险**：`HandoffDirective` 的校验器强制——只要
`next_capability` 是广告能力，`routing_mode` 必须是 `HUMAN_ONLY`，
写别的值直接抛异常。

**需要 Owner 决定的**：什么时候、以什么条件把开关打到 `ENABLED`。
按交接包，这需要 H3 批准并单独立项。

## D-03：`OperatingUnitRef` 里的 `shop_account`

| 来源 | 字段集 |
|---|---|
| 方案 B §6 | `operating_unit_id, shop_id, shop_account, site_code, parent_asin, parent_seller_sku` |
| 契约 A `operating-unit-ref.v2.schema.json` | `contract_version, operating_unit_id, shop_id, site_code, parent_asin, parent_seller_sku`，且 `additionalProperties: false` |

方案多了一个 `shop_account`（ERP 账号字符串，MCP 取数需要它）。
但契约禁止额外字段，塞进去导出的 JSON 会直接校验失败。

**采用**：**拆成两个对象。**

- `OperatingUnitRef`（`core/contracts.py`）—— 严格等于契约，可导出、可共享；
- `OperatingUnitBinding`（`core/operating_unit.py`）—— 中控经营单元业务键
  `shop_id + parent_asin + parent_seller_sku`、站点属性 + `shop_account`，
  只在进程内用于取数，**不进任何跨服务契约对象**。

交接包原话是「不得用数据库临时字段或提示词绕过契约语义」，
把取数账号塞进身份契约正是这类绕过。

**影响**：`FactCollector.collect()` 接 `OperatingUnitBinding`，
`FactSnapshotBuilder.build()` 接 `OperatingUnitRef`。
`shop_account` 另存于快照的 `identity` 域（那是自由 dict，不受契约约束）。

## D-04：审批等级只有 H2/H3 vs 契约的 H0–H3

| 来源 | 取值 |
|---|---|
| 方案 B §6 `ProposedAction.approval_level` / `DecisionProposal.approval_level` | `Literal["H2", "H3"]` |
| 契约 A `operating-policy-registry.human_gates` | `H0, H1, H2, H3` |

**采用**：完整 `HumanGate`（H0–H3）。

**理由**：数据刷新、复扫这类动作按交接包 04 §3 是 H0；
清货下一价格档是 H1（PREAUTHORIZED）。把类型限死在 H2/H3
会让这些动作无法表达。

**实际行为不变**：`ProposalBuilder` 的默认门仍是 H2，
按规则升到 H3。当前不会产出 H0/H1 的经营动作。

**额外加了一条方案没有的约束**：`DecisionProposal` 的校验器强制
整份建议的门 ≥ 任一动作的门。交接包 04 §3.1 说
「Agent 可以建议提高门槛，不能自行降低」——现在写进类型系统了。

## D-05：巡检信号字段名

| 来源 | 字段名 |
|---|---|
| 交接包 `knowledge/06`、`设计_v1.3/08` 的叙述 | `child_scope_exception`、`evidence`、`suggested_protective_action`、`lifecycle_status` |
| 契约 `inspection-signal.v2.schema.json` | `child_scope`、`evidence_refs`、`signal_state`（且 `additionalProperties: false`） |

**采用**：契约字段名。用叙述里的名字会直接校验失败。

`AnomalySignal`（内部表示）保留了 `lifecycle_status` 作为属性名，
但它不是契约对象；转成 `InspectionSignal` 时映射到 `signal_state`。

## D-06：队列时点枚举 `DUE_NOW`/`WATCH`

交接包 05 §5.2 的伪代码里写了 `derive_timing()` 返回
`OVERDUE / DUE_NOW / SCHEDULED / WATCH`，但契约枚举是
`OVERDUE / DUE_TODAY / DUE_SOON / SCHEDULED / MONITOR_ONLY`。

**采用**：契约值。

## D-07：MCP SDK 函数签名

方案 §7 的示例代码：

```python
from mcp.client.streamable_http import streamable_http_client
async with streamable_http_client(self.url, headers=self.headers) as (r, w, _):
```

官方 SDK 1.27 起 `streamable_http_client` 的签名改为接受预配置的
`httpx.AsyncClient`（旧签名保留在 `streamablehttp_client`）。

**采用**：新签名 + 复用同一个 httpx 客户端。

**顺带好处**：连接池被复用，正好满足方案里
「生产环境应考虑复用 MCP Session」的要求（首版仍是每次调用开新 Session）。

---

## D-08：`inspector_main` 私有函数依赖

方案 §12 明确允许第一阶段直接调用私有函数：

> 第一阶段可以直接调用原函数，稳定后再拆除私有函数依赖。

**采用**：照做。`LegacyRuleAdapter` 通过延迟 import 调用
`_detect_with_local_data` 与 `_grade_performance_anomalies`。

**已验证**：这两个函数是**纯函数**——只消费传入的 dict 和聚合对象，
不自己查库。所以适配器不需要 SQLite 就能跑，测试跑得很快。

**风险**：改 `inspector_main.py` 时可能碰坏适配器。
`tests/unit/test_legacy_regression.py` 的 14 个用例是这条边界的护栏。

## D-10：交接包内部自身的不一致（我按契约实现，供参考）

这些是交接包**内部**的冲突，不是方案与交接包的冲突，一并记录：

| 项目 | 冲突 | 我的取舍 |
|---|---|---|
| 新品验证阶段 | 注册表/Schema 是 6 阶段；`设计_v1.3/01` 是 4 阶段 | 用 Schema 的 6 阶段 |
| 初始化状态 | Schema 6 值；`05 §4.2` 写 `DRAFT/EVIDENCE_READY/RECOMMENDED/H2_PENDING` | 用 Schema |
| 结果状态 | `05 §4.2/§5.3` 出现 `PENDING_DATA/PARTIAL/ADVERSE`，不在契约枚举里 | 用契约的 `INCONCLUSIVE/PARTIAL_SUCCESS/ADVERSE_EFFECT` |
| 行动状态 | `05` 的 `READY/ISSUED/SUCCEEDED/...` vs 契约 6 值 | `DecisionReview.execution_status` 用契约 6 值；ActionOrder 内部状态不在巡检职责内 |
| `approval_paths` | 注册表 4 值（含 `PREAUTHORIZED`）；初始化 Schema 只允许 3 值 | 枚举取注册表全集，写初始化对象时排除 `PREAUTHORIZED`，代码里有注释 |
| `risk_level` | 只有 H1–H3，没有 H0，与 `human_gates` 不同 | 保持区分，未合并 |

建议这几处由交接包维护方在下一版统一，否则每个实现方都要各自判断一次。
