# S3 主链路收敛实施报告

> 日期：2026-07-31  
> 状态：S3 退出条件通过  
> 实施基线：`docs/07-巡检AgentV2最终改造实施方案.md`

## 交付结果

- 新增纯巡检主编排器，只执行 MCP 事实采集、质量检查、快照、R2/R3、生命周期对账、MySQL 保存和 Outbox；
- Mode Agent、广告 Agent、经营建议、审批、复盘和 LLM 不进入新巡检组合根；
- API、Worker 和正式兼容命令 `python -m integrations.worker` 均切至 MySQL 主链路；
- 人工巡检的客户端 request、trace 和初始化状态进入持久化 Job，内部重试 request 独立生成；
- 同一幂等键仅允许完全相同的业务日期、经营范围、规则版本和 scope 重放；
- 新增 Job、批次真实聚合状态、Run + Outbox 投递状态和 Signal + occurrence 历史查询；
- Run 先落 `RECEIVED`，成功时 Snapshot、Signal、Occurrence 和 Outbox 原子提交，异常时 Run 落 `FAILED`；
- 初始化未完成不阻断事实巡检，但异常信号明确标记 `BLOCKED_DEPENDENCY`；
- 旧 SQLite 与越界模块保留用于历史兼容，但正式 Worker 入口不再触达。

## 端到端验证

真实 MySQL 测试由正式 `MySqlRuntimeWorker` 完成领取、编排和成功回写：

1. 创建单经营单元人工批次及 Job；
2. 验证完全相同请求返回原批次，scope 漂移返回幂等冲突；
3. 验证客户端 request、trace、初始化状态从 API 语义传入 Job；
4. Fake MCP 完整调用当期声明的全部事实工具（S3 验收时 8 个，S4 扩展后 10 个）；
5. 运行 R2/R3 和生命周期对账；
6. 在 MySQL 原子保存 Run、Snapshot、Signal、Occurrence 和 Outbox；
7. Worker 将 Job 和 Batch 聚合为成功；
8. 结果封套不含模式、广告、建议、审批或 LLM 字段；
9. 初始化未完成时，非数据质量信号均为 `BLOCKED_DEPENDENCY`；
10. 清理验证数据后确认 11 张表结构正常且业务表为空。

## 运行边界

S3 完成表示单经营单元的 API → MySQL Job → Worker → 纯巡检编排器 → 原子保存主链路已收敛。
`feature_flags.scheduler_enabled` 仍为 `false`：S4 已实现 #30 清单分页和事实 Adapter，但 #30
缺父级身份，#9 又依赖尚未确定的权威负责人名册。冻结运行枚举策略并完成真实样本规则回归后
才能开启自动调度。S5 的 Result Sink、
Outbox ACK 和 Feedback Inbox，以及 S6 预检、监控、灰度和回滚底座现已完成内部实现；正式
MCP、结果接收端和反馈合同尚未冻结，因此不能进入 `CANARY/FULL`。
