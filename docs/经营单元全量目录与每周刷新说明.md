# 经营单元全量目录与每周刷新说明

## 数据来源

- 默认使用 `erp_amazon_listing_query_page` 全量分页读取；V3 约定每条
  `records[].asin`、`records[].sellerSku` 就是父 ASIN/父 SKU。
- 该路径不读取运营配置表，也不调用负责人目录 MCP；`userId` 仅作为负责人 ID 快照。
- 原始全量目录保存于 `t_patrol_listing_catalog`，保留 ERP 返回的所有可识别状态（包括 `ACTIVE`、`ONLINE`、`INACTIVE`、`OFFLINE`、`DISABLED`）的子 ASIN/SKU、店铺、站点、负责人和 MCP 返回的父级字段。
- 可巡检目录保存于 `t_patrol_operating_unit_catalog`，只投影同时具备可信 `parentAsin`、`parentSellerSku` 的记录；经营状态不再作为排除条件，缺失数据的单元仍需巡检并传递数据缺口。
- `asin/sellerSku` 按 V3 业务合同直接映射为父级身份。
- 可巡检目录唯一键是 `shopId × siteCode × parentAsin × parentSellerSku`，不读取运营配置表。

## 持久化

目录保存于巡检库的 `t_patrol_listing_catalog`（全量源）和 `t_patrol_operating_unit_catalog`（可巡检投影），包含完整取数绑定和负责人 ID 快照。
刷新采用“先从 MCP 完整读取，成功后事务替换”的方式，不会留下半批目录；失败时保留已有目录，首次没有旧目录则阻止全量巡检。

## 更新周期

`operating_unit_catalog.refresh_interval_days` 默认是 `7`。调度器或批量巡检启动时检查目录时间：

- 没有目录：立即全量刷新，首次失败则阻止全量巡检；
- 已超过 7 天：立即全量刷新；
- 未超过 7 天：直接使用当前目录，不重复请求全量 MCP。

## 批量巡检

每次需要重新巡检全部经营单元时，使用统一入口：

```bash
./scripts/run_full_patrol.sh
```

该入口会先完整刷新 ERP 目录，再按每批最多 50 个经营单元执行巡检并投递中控；不会根据历史巡检记录跳过单元。脚本带互斥锁，同一时间重复启动会直接退出；日志保存到 `logs/full-patrol-<时间>.log`。可通过 `PATROL_CONCURRENCY` 调整巡检并发数。

运行全部有效经营单元：

```bash
./.venv/bin/python -m scripts.run_real_patrol_batch \
  --all-active \
  --concurrency 4
```

手动立即刷新目录：

```bash
./.venv/bin/python -m scripts.refresh_operating_unit_catalog
```

也可以用 `--count N` 从当前全量目录中取前 N 条做小批量验证。目录刷新失败时，若已有完整目录则继续使用该旧快照并记录告警；没有目录时不回退到历史 `t_patrol_job` 猜身份。

刷新输出中的 `source_records` 是全量子体记录数，`units` 是已经具备父 ASIN/父 SKU、可以安全巡检的经营单元数。

批量巡检完成后会自动按每批最多 50 个经营单元构造中控 v2 载荷，执行经营模式查询/自动评估闭环，写入持久化 Outbox，并等待 `submit_patrol_batch` ACK。命令只有所有中控批次状态均为 `DELIVERED` 才返回成功；中控暂时不可用时按 Outbox 退避策略重试，业务拒绝或合同错误立即失败。没有真实异常、无法满足中控 `proposal.anomalies` 合同的单元不会伪造异常，会明确报出不可提交原因。
