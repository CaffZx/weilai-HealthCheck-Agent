# 待冻结事项清单与工程默认值

> 对应改造方案 v1.0 §28「开发前需要冻结」的 12 项，
> 以及交接包《01-人工确认清单》里尚未填写的业务参数。

## 怎么读这份文档

交接包写得很清楚：**「技术部门不得自行补阈值」**、
**「未确认阈值和授权额度保持显式待决，不得由 Agent 自行补全」**。

所以本次交付把待定事项分成三类，处理方式不同：

| 类型 | 处理方式 | 在代码里长什么样 |
|---|---|---|
| **A. 业务数值** | 一律**留空**，不填默认值 | 配置里写 `null` + `待确认: true`；代码遇到 null 时降级为观察，不产生可审批动作 |
| **B. 工程默认值** | 填了一个可工作的值，**显式标注待拍板** | 配置或常量旁边有 `⚠ 待冻结事项 F-xx` 注释 |
| **C. 架构选择** | 做成可替换的接口，**当前给一个实现** | 定义 Protocol，提供默认实现，换实现不用改上游 |

拍板前可以正常跑，但 **A 类未确认的判定不会进入自动审批**。

## 关键机制：留空是怎么传导到最终结论的

这是本次交付最需要被理解的一条设计。以观察窗口为例：

```text
config/proposal_rules.yaml: days = null
    ↓
ProposalBuilder._observation_window() → None
    ↓
DecisionProposal.observation_window_days = None
    ↓
SuccessCriterion.threshold = None，note 里带 [待确认]
    ↓
复盘时 _evaluate_criteria() → GuardrailResultStatus.UNKNOWN
    ↓
ReviewOrchestrator 检测到 UNKNOWN → outcome_status = INCONCLUSIVE
    ↓
DecisionReview.automatic_judgement = False，走人工复核
```

**结果：阈值没拍板的判据，永远不会被自动判成"成功"或"失败"。**
不会有"因为默认值是 7 天所以判定失败"这种事故。

`SuccessCriterion` 的校验器还强制：threshold 为 None 时 note 必须带 `[待确认]`，
杜绝"忘了填"被当成"没有门槛"。相关测试：
`test_unconfirmed_threshold_yields_inconclusive`、
`test_unconfirmed_observation_window_stays_none`。

## 建议的拍板顺序

交接包 01 §C 给的顺序是 `B01 → B02 → B07 → B03 → B04 → B05 → B06 → B08`，
并且规定：**前两项和 B07 未确认前，不应启用自动模式迁移或真实结果自动判定。**

从技术侧看，最挡路的是这四项：

1. **F-06**（中控 PatrolAnalysisPackage 最终 Schema）—— 不定，两边合同会各自演进；
2. **F-03**（MCP 清单身份和分页合同）—— Scheduler 已实现；合同不定则不能安全启用 10,000 单元生产调度；
3. **F-02**（任务队列选型）—— 不定，上线前要重做一次队列层；
4. **B03 观察窗口** —— 不定，复盘永远只能出 INCONCLUSIVE。

前三项是技术负责人可以拍的，第四项需要业务 Owner。
