### 2.1 经营单元清单

现有 Provider 固定调用 `erp_amazon_listing_query_page`，请求字段为 `pageNo`、`pageSize`，单页
最大 20。文档确认它可做无筛选全量分页，并返回 `shopId/shopAccount/siteCode/userId`、子 ASIN/SKU
和状态，但没有声明父 ASIN/父 Seller SKU。因此它目前只能作为“子在线列表”，不能直接作为
`shop × site × parent ASIN` 经营单元清单。

运行枚举需在以下两种方案中冻结一种：

1. 扩展 `erp_amazon_listing_query_page`，使每条记录同时提供可信 `parentAsin` 和
   `parentSellerSku`；现有 Provider 可继续使用；
2. 改用 `erp_listing_follow_up_by_principal` 聚合。该 Tool 已明确返回父子身份、状态，最大
   `pageSize=200`；备用 Provider 已实现。运行时需通过 `AZLISTING_PRINCIPAL_SCOPES_JSON` 提供
   `principalName/principalUserId/shopId/shopAccount/siteCode` 权威映射，不能从已隔离的旧 SQLite 读取；该路径
   还需补充数字负责人 ID 映射，负责人姓名不能替代中控用户 ID。

最终运行清单响应必须提供稳定分页，每条经营单元至少包含或可确定：

- `shopId`：正整数，跨 Tool 含义一致；
- `shopAccount`：后续事实 Tool 的取数账号；
- `siteCode`：可归一为标准 Amazon 站点；
- `parentAsin`：可信父 ASIN，不允许用子 ASIN回填；
- `parentSellerSku`：可信父 Seller SKU；
- `status`：正式有效值及 Active/Inactive 映射。
- `ownerUserIds`：从每条 `userId` 聚合出的非空正整数集合；同一经营单元允许多人负责，集合
  不参与经营单元唯一键。中控单值 `ownerUserId` 如何选择主负责人仍需冻结。

必须用四组真实脱敏运行样例验证：正常跨页、同父体跨页重复、Inactive、分页过程中总数变化。
同一 `shopId + siteCode + parentAsin` 映射到不同取数绑定时，巡检会整批拒绝。

2026-08-04 测试网关验收确认：当前 Key 能发现 #30 清单 Tool，但调用返回
`MCP_PERMISSION_DENIED`；#30 字段字典也明确没有父 ASIN/父 Seller SKU。#9 可作为父级身份来源，
但尚无经 Owner 确认的非 SQLite 权威负责人/店铺/站点映射。因此运行枚举门禁未通过。

### 2.3 脱敏样本验收

MCP Owner 提供一份符合 `contracts/mcp-input-acceptance-sample.v1.schema.json` 的真实脱敏响应 JSON，
可从 `contracts/examples/mcp-input-acceptance-sample.v1.example.json` 复制结构后替换样本值。
样本不得包含 MCP 地址、Token 或真实店铺账号；应包含清单分页响应、一个样本经营单元身份和
该单元十一个固定事实 Tool 及扩展 Tool 的 `data` 数组。巡检侧执行：

```bash
.venv/bin/python -m scripts.validate_mcp_input_sample /path/to/redacted-sample.json
```

验收器只读本地文件，不连接 MCP。它复用生产 Provider、Normalizer 与 Quality 逻辑，并验证：

- 父 ASIN/父 Seller SKU、分页总数、Active/Inactive 与重复绑定；
- `erp_asin_full_detail` 显式返回当前父 ASIN，不接受请求参数兜底；
- 十一个固定 Tool 齐全，四个核心 Tool 非空，关键归一化字段可取得；
- 任一 Tool 出现的店铺、站点、父 ASIN、父 Seller SKU、取数账号不得与样本单元冲突；
- 输出阻断缺口、可降级缺口、未映射字段和 SourceRef 数量。

只有退出码为 0、`status` 为 `ACCEPTED` 或 `ACCEPTED_WITH_GAPS`、
`blocking_gap_count=0` 且全部 `critical_field_coverage=true` 才算样本门禁通过。可降级缺口仍需
MCP Owner 确认是否属于正式合同限制，不能由巡检侧静默视为完整覆盖。

### 2.4 经营模式 Agent

经营模式 Agent MCP 不是经营单元清单接口。它按已知的
`shop_id + parent_asin + parent_seller_sku` 查询或判断该单元的经营模式：

- 巡检允许调用批量只读 `get_current_operating_modes`，未命中时调用自动任务 `start_operating_mode_evaluation_job` 并轮询状态；
- 巡检禁止调用会执行 G0-G8 判断并写库的 `evaluate_operating_mode`；
- `DECIDED` 结果可进入中控 `businessModel/recommendedBusinessModel/modeReasonSummary`；
- `BLOCKED`、`NEEDS_HUMAN_REVIEW` 或 `null` 不生成默认模式；
- 源枚举 `ACTIVE_ADVANCE` 显式映射为中控 `CONTROLLED_GROWTH`，源值保留在原始分析中；
- 查询结果不包含置信度，巡检不得伪造 `modeConfidence`。

2026-08-04 已通过真实 `initialize + tools/list`，并对三个已巡检经营单元执行只读查询，三者
均返回 `null`。要生成首次模式，经营模式 Owner 需提供并确认完整 `PolicyContext`，由其调用
写入型 Tool 保存判断；巡检不拥有该策略上下文和决定权。

## 3. Result Sink 合同冻结

请求体以 `contracts/inspection-result-envelope.v1.schema.json` 为唯一 Schema。接收端不得要求
经营模式、建议、动作、审批或综合分字段。建议使用 HTTP POST；若使用 MCP Tool，业务参数
仍必须原样承载该 Envelope，不能转换为旧 `submit_patrol_batch.units[].proposal`。

请求头冻结为：

- `Authorization: Bearer ...`；
- `Idempotency-Key: {outbox_id}`；
- `X-Content-Hash: {冻结 payload 的 SHA-256}`；
- `Content-Type: application/json`。

响应以 `contracts/inspection-result-ack.v1.schema.json` 为唯一 Schema，并满足：

- `event_id` 与 Outbox Envelope 的事件 ID 一致；
- `accepted=true` 才能标记发布成功；
- `accepted_object_ids` 覆盖 Run、全部 Signal 和 Handoff ID；
- `rejected_objects` 非空或缺少必需对象时视为业务失败；
- 同幂等键同内容返回 `duplicate=true` 的成功 ACK；
- 同幂等键不同内容返回明确幂等冲突，不覆盖已接收内容。

## 4. Feedback Event 合同冻结

请求体以 `contracts/inspection-feedback-event.v1.schema.json` 为唯一 Schema，入口为
`POST /internal/v1/patrol/feedback-events`，使用独立 Feedback Bearer Token。

需冻结以下事件及语义：

| 事件 | 必需补充 | 巡检侧行为 |
|---|---|---|
| `HANDLING_STARTED` | 当前 `signal_version` | 转处理中 |
| `HANDLED` | `next_inspection_at` 或采用 R7 默认 | 转待复扫，不直接恢复 |
| `OBSERVE_REQUESTED` | 观察时间或采用 R7 默认 | 转观察中 |
| `IGNORED` | `payload.reason_code` | 记录忽略 |
| `FALSE_POSITIVE` | `payload.reason_code` | 记录误报 |
| `ACTION_RECEIPT_AVAILABLE` | `action_receipt_ref` | 只记回执，不改状态 |
| `UNIT_ARCHIVED` | `payload.reason_code` | 归档单元信号 |

中控必须按当前 Signal 版本发送；旧版本返回 `SIGNAL_VERSION_CONFLICT`，不得静默覆盖。
同 `event_id` 同内容为重复成功，不同内容为 `IDEMPOTENCY_CONFLICT`。

## 5. 真实 E2E 验收

在专用联调环境按顺序验证：

1. MCP 正常跨页清单 → Scheduler 只创建一个幂等 Batch；
2. 50 条以上单元 → 一个业务 Batch、Job 分块写入，无重复经营单元；
3. 十个 Tool 完整事实 → Run、Snapshot、Signal、Occurrence、Outbox 原子落库；
4. 核心 Tool 缺失 → 明确数据阻断；可降级 Tool 缺失 → 明确 Data Gap；
5. Result Sink 首投失败后重投原包，内容哈希不变；
6. Result Sink 同键重复 ACK 成功、异内容冲突；
7. `HANDLED` Feedback → `AWAITING_RESCAN`，到期 Scheduler 创建复扫 Job；
8. 新事实连续两次未命中才恢复，不把“已处理”当“已恢复”；
9. 旧版本、未知 Signal、非法跳转和缺原因码均拒绝并留 Inbox 审计；
10. 联调后核对无 `t_ops_*` 直写、无凭据落盘、测试数据按清单精确清理。
