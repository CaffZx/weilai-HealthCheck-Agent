# 原始事实 MySQL 归档与复用实施报告

> 日期：2026-08-03  
> 状态：代码、迁移及真实 MySQL 验证通过  
> Schema Revision：`0004_raw_fact_archive`

## 1. 改造目标

巡检每次从 MCP 获得的事实不仅用于当轮计算，还必须能够在 MySQL 中完整复查、复现和
受控复用。本次改造将原有“标准化快照 + 来源哈希”升级为：

```text
MCP 完整原始响应
→ Raw Fact 不可变归档
→ 归一化和质量检查
→ Fact Snapshot 冻结
→ 规则巡检与信号生命周期
```

## 2. 数据模型

新增 `t_patrol_raw_fact`，每个 Run、每个事实工具一条记录。当前一轮完整巡检固定产生
10 条原始事实记录。

保存内容包括：

- 完整 MCP 请求参数及 SHA-256；
- 完整 MCP 响应封套；
- 从响应封套抽取的数据数组及 SHA-256；
- 工具名、事实键、经营单元、业务日期和实际采集时间；
- 是否核心事实、行数、耗时、警告；
- 失败状态、错误码和错误信息；
- 所属 Run、Fact Snapshot 和历史复用来源。

唯一约束为 `(run_id, fact_key)`。成功与失败记录分别通过 CHECK 约束保证字段组合合法。

## 3. 写入时序

1. Worker 创建 `t_patrol_run`；
2. Collector 并行调用全部 MCP 工具；
3. Collector 返回后立即独立事务写入 `t_patrol_raw_fact`；
4. 即使后续归一化、规则或信号处理失败，已采集的原始证据仍然保留；
5. 成功生成 Fact Snapshot 后，在最终事务中将 Raw Fact 关联到 `snapshot_id`；
6. `t_patrol_fact_snapshot.raw_reference_json` 同时保存 `raw_fact_id` 定位信息。

## 4. 查询和复用

完整事实查询接口：

```http
GET /api/v1/patrol/runs/{run_id}/facts
```

默认巡检始终实时调用 MCP，不自动使用缓存。人工需要复现历史判断时，可以在创建巡检
请求中显式传入：

```json
{
  "reuse_fact_run_id": "pr_0123456789abcdef01234567"
}
```

复用前必须同时满足：

- 来源 Run 属于同一经营单元；
- 10 类事实完整且全部成功；
- 来源查询参数与当前经营单元绑定完全一致；
- 请求哈希和响应内容哈希复算通过。

复用不会修改旧数据，而是为新 Run 创建 10 条新记录，通过
`reused_from_raw_fact_id` 保留完整血缘，并沿用原业务日期和原采集时间。

## 6. 运维边界

- 原始响应可能包含店铺经营数据，应限制查询接口权限并记录访问审计；
- MySQL JSON 会增加容量，生产前应冻结保存周期、归档和清理策略；
- 不允许通过复用参数绕过经营单元身份匹配和内容哈希校验；
- 原始事实只用于复查和显式复现，日常巡检仍以实时 MCP 数据为准；
- 数据库备份、脱敏导出和日志系统不得泄露 MCP Token 或数据库口令。
